# 観測データと海洋モデル：時刻・単位・鉛直座標

位置推定の前に、タグと環境データが同じ物理量を比較しているかを確認する。ファイルに同名の列があるだけでは、時刻の基準、圧力と水深、海面と海底の基準面は一致しない。

## 1. 入力を整理する

| 入力 | 科学的な役割 | 確認する情報 |
|---|---|---|
| タグの温度・圧力・深度 | 魚が経験した環境 | 単位、校正、記録間隔、時刻ずれ、欠測、センサー位置 |
| 放流・再捕・死亡等のイベント | 既知位置に関する情報 | イベント種別、緯度経度、位置と時刻の不確かさ |
| 音響検出 | 受信機付近にいた情報 | タグID、受信機ID、受信時刻、誤検出処理 |
| 受信機設置記録 | 未検出を解釈する条件 | 設置・回収、停止、移設、受信範囲の試験 |
| 海洋モデル | 温度、海面高度、鉛直座標 | 変数の定義、時刻の意味、時間境界、海陸マスク |
| 海底地形 | 潜れる深さの制約 | 鉛直基準面、格子間隔、元の測量情報、符号 |
| 潮汐調和定数 | 潮位変動の予測 | 振幅単位、位相規約、時刻基準、分潮、版 |

上表は研究相談のための整理であり、すべてを自動検査するAPIの仕様ではない。実装が受け取る列名やイベント名は、対象コミットの入力形式に合わせる。`af4fe17` の `docs/format.md` では、`dst.csv` は `time`・`temperature`・`pressure` の列、`tagging_events.csv` は `event_name`・`time`・`latitude`・`longitude` の列、`acoustic.csv` は `deployment_id` と `time` を必須とする。`stations.csv` は受信機の設置・回収の時刻と位置（`deploy_*`、`recover_*`）を持つ。なお `compute_emission_pdf` が読むイベントは `release` と `fish_death` で、`recapture` の行は読まない（`helpers.py` の該当箇所）。`fish_death` の緯度経度が `NA` なら、終端位置の制約は作られない。

## 2. UTCとモデルの時間ビン

タグの10分値、潮汐の時間値、水温の日平均値は、それぞれ異なる時間尺度を持つ。タグの値をどの日・どのモデル時間区間に割り当てたかで、比較される環境が変わる。

`compute_diff`は、参照モデルの時刻境界（time bounds）から作った時間ビンに従ってタグをグループ化する。日付ラベルだけを見て午前0時を瞬時値と解釈しない。日本時間で記録した観測をUTCに直す場合、元のタイムゾーンと変換履歴を残す。潮汐では位相の整合にも影響する。

同じ日の平均温度でも、魚は移動し、深さを変えている。日ごとの重みは「その一日を一つの位置状態で代表させる」という離散化を伴う。この近似が妥当かは、記録間隔、移動尺度、環境の変化から判断する。

**図を追加する場合の実データ例：** タグの生時系列、モデルの時間ビン、ビンごとの有効サンプル数を上下に並べる。欠測した日と、観測はあるがどの候補位置とも整合しない日を別に表示する。

## 3. `pressure`という列名を水深の単位と取り違えない

デモの`pressure`列は、正の下向き水深としてそのまま計算に使われる。新しいタグの圧力がdbarなら、列名を合わせる前に変換方針を決める。

TEOS-10のGSWでは`gsw_z_from_p`の入力は海水圧[dbar]と緯度、出力は上向きを正とする高さ[m]であり、水深はその符号を反転した量になる。絶対圧か海水圧かも確認する。厳密な換算は緯度等に依存するため、「1 dbar = 1 m」を定義として埋め込まない。[TEOS-10 / GSW公式資料](https://www.teos-10.org/pubs/gsw/v3_04/html/gsw_z_from_p.html)

位置が未知なら、換算に使う緯度にも不確かさがある。最初は観測海域を代表する緯度による換算を明記し、必要なら候補域内の緯度差による影響を感度分析する。これは新しいデータを準備するときの提案であり、現行Pangeo-Fishが自動で実施するという意味ではない。

## 4. 鉛直座標と海面高度

静的水深を$H_0>0$、平均海面等を基準とした海面高度を$\eta$とすると、水柱の厚さは同じ基準面・符号の下で$H_0+\eta$と表せる。海面からのタグ深度と、固定基準面からの海底深度を直接比較すると、潮汐や海面変動の分だけ意味がずれる。

`af4fe17` のモデル前処理（`_set_dynamic_depth`）は、モデル製品に応じて鉛直座標を次のように変換し、瞬間的な海面からの各層の深さ `dynamic_depth` を作る。

| 対象 | コードの処理 | 読む際の注意 |
|---|---|---|
| geopotentialの深度（全球製品など） | $z+XE$ | `XE`の単位・符号・基準面を入力資料と照合する |
| `zstar`（IBI の再解析・時間値） | $z\max(0,(H_0+XE)/H_0)$ | 同じ「深度」という名前でも固定深度と同一ではない |
| NWSの特例 | 表面（`depth=0`）を0に保ち、それ以外は $z+XE$ | 地域モデル固有の取り扱いを一般化しない |
| `min_water_depth="auto"` | $H_0+XE\le 0$の干出セル・時刻の`diff`を欠測にする | 有効な湿ったセルが一つもない時間スライスは、マスクせずに残す保護処理がある |

この表は実装の説明であり、上記の式を任意のROMSや他モデルにそのまま適用してよいという推奨ではない。特にσ座標を持つモデルでは、格子、変換式、基準海面、海底深度をモデル仕様に合わせて読む。

## 5. IBIとGLORYSを使い分ける

IBI再解析`IBI_MULTIYEAR_PHY_005_002`はIberia–Biscay–Irelandを対象とする地域プロダクトで、水平格子は1/36°（約3 km）である。GLORYS12V1の`GLOBAL_MULTIYEAR_PHY_001_030`は全球1/12°（約9 km）の再解析である。製品ID、個別dataset ID、変数、時間平均の種類、取得版は分けて記録する。[IBI公式製品ページ](https://data.marine.copernicus.eu/product/IBI_MULTIYEAR_PHY_005_002/description)／[GLORYS公式製品ページ](https://data.marine.copernicus.eu/product/GLOBAL_MULTIYEAR_PHY_001_030/description)

フランス沿岸のデモで使ったIBIは、日本周辺を含むモデルではない。日本の事例へ移るときは、GLORYSまたは適切な地域モデルの被覆、沿岸・浅海の再現性、利用可能な変数を確認する。FRA-ROMSは本資料では入力適合性の検討対象であり、実行済みの接続例としては扱わない。

海洋モデルの格子を細かいHEALPixに補間しても、新しい観測情報が増えるわけではない。温度構造の識別力と誤差の大きさを、格子間隔とは別に評価する。

## 6. 欠測、ゼロ、海陸マスク

値0は有効な温度・海面高度であり得る。NaNは欠測や除外を表す。候補海域外や陸上、入力の不足、観測と矛盾するセルを、同じゼロとして一括処理しない。

複数の観測重みを掛け合わせる`combine_emission_pdf`は`skipna=False`で積を取るため、ある項が欠測のセルは積も欠測になり、そのセルは消える（観測重みが一つだけの場合は積を取らない）。また、`optimize_pdf`と、状態確率・経路の計算が読み込む観測重みについては、正の質量が残らない時刻をHMM実行前に検出してエラーにする（`_check_emission_mass`）。`normalize_pdf`自体は警告を出すだけである。潮汐関数の一様重みへのフォールバックは、その関数の定義であり、あらゆる欠測を自動で解決する一般ルールではない。

新しいデータでは、入力変換後の観測数、各観測重みが定義されるセル数、共通の日時・cell ID、正の重みの総量を図示する。これは地図上の経路を見る前に行う診断になる。
