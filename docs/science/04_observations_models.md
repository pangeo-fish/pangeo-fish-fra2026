# 観測データと海洋モデル：時刻・単位・鉛直座標

位置推定の前に、タグと環境データが同じ物理量を比較しているかを確認します。ファイルに同名の列があるだけでは、時刻の基準、圧力と水深、海面と海底の基準面は一致しません。

## 1. 入力を整理する

| 入力 | 科学的な役割 | 確認する情報 |
|---|---|---|
| タグの温度・圧力・深度 | 魚が経験した環境 | 単位、校正、記録間隔、時刻ずれ、欠測、センサー位置 |
| 放流・再捕・死亡等のイベント | 既知位置に関する情報 | イベント種別、緯度経度、位置と時刻の不確かさ |
| 音響検出 | 受信機付近にいた情報 | タグID、受信機ID、受信時刻、誤検出処理 |
| 受信機設置記録 | 未検出を解釈する条件 | 設置・回収、停止、移設、受信範囲の試験 |
| 海洋モデル | 温度、海面高度、鉛直座標 | 変数の定義、時刻の意味、時間境界、海陸マスク |
| 海底地形 | 潜れる深さの制約 | 鉛直基準面、格子間隔、元の測量情報、符号 |
| 潮汐調和定数 | 潮位変動の予測 | 振幅単位、位相規約、時刻基準、分潮、版 |

上表は研究相談のための整理であり、すべてを自動検査するAPIの仕様ではありません。実装が受け取る列名やイベント名は、対象コミットの入力形式に合わせます。`af4fe17` の `docs/format.md` では、`dst.csv` は `time`・`temperature`・`pressure` の列、`tagging_events.csv` は `event_name`・`time`・`latitude`・`longitude` の列、`acoustic.csv` は `deployment_id` と `time` を必須とします。`stations.csv` は受信機の設置・回収の時刻と位置（`deploy_*`、`recover_*`）を持ちます。なお `compute_emission_pdf` が読むイベントは `release` と `fish_death` で、`recapture` の行は読みません（`helpers.py` の該当箇所）。`fish_death` の緯度経度が `NA` なら、終端位置の制約は作られません。

## 2. UTCとモデルの時間ビン

タグの10分値、潮汐の予測値（`healpix` 方式は1時間平均、`pedersen` 方式は10分サンプルのまま比較）、水温の日平均値は、それぞれ異なる時間尺度を持ちます。タグの値をどの日・どのモデル時間区間に割り当てたかで、比較される環境が変わります。

`compute_diff`は、参照モデルの時刻境界（time bounds）から作った時間ビンに従ってタグをグループ化します。日付ラベルだけを見て午前0時を瞬時値と解釈しません。日本時間で記録した観測をUTCに直す場合、元のタイムゾーンと変換履歴を残します。潮汐では位相の整合にも影響します。

同じ日の平均温度でも、魚は移動し、深さを変えています。日ごとの重みは「その一日を一つの位置状態で代表させる」という離散化を伴います。この近似が妥当かは、記録間隔、移動尺度、環境の変化から判断します。

**図を追加する場合の実データ例：** タグの生時系列、モデルの時間ビン、ビンごとの有効サンプル数を上下に並べます。欠測した日と、観測はあるがどの候補位置とも整合しない日を別に表示します。

## 3. `pressure`という列名を水深の単位と取り違えない

デモの`pressure`列は、正の下向き水深としてそのまま計算に使われます。新しいタグの圧力がdbarなら、列名を合わせる前に変換方針を決めます。

TEOS-10のGSWでは`gsw_z_from_p`の入力は海水圧[dbar]と緯度、出力は上向きを正とする高さ[m]であり、水深はその符号を反転した量になります。絶対圧か海水圧かも確認します。厳密な換算は緯度等に依存するため、「1 dbar = 1 m」を定義として埋め込みません。[TEOS-10 / GSW公式資料](https://www.teos-10.org/pubs/gsw/v3_04/html/gsw_z_from_p.html)

位置が未知なら、換算に使う緯度にも不確かさがあります。最初は観測海域を代表する緯度による換算を明記し、必要なら候補域内の緯度差による影響を感度分析します。これは新しいデータを準備するときの提案であり、現行Pangeo-Fishが自動で実施するという意味ではありません。

## 4. 鉛直座標と海面高度

静的水深を$H_0>0$、平均海面等を基準とした海面高度を$\eta$とすると、水柱の厚さは同じ基準面・符号の下で$H_0+\eta$と表せます。海面からのタグ深度と、固定基準面からの海底深度を直接比較すると、潮汐や海面変動の分だけ意味がずれます。

`af4fe17` のモデル前処理（`_set_dynamic_depth`）は、モデル製品に応じて鉛直座標を次のように変換し、瞬間的な海面からの各層の深さ `dynamic_depth` を作ります。

| 対象 | コードの処理 | 読む際の注意 |
|---|---|---|
| geopotentialの深度（全球製品など） | $z+XE$ | `XE`の単位・符号・基準面を入力資料と照合する |
| `zstar`（IBI の再解析・時間値） | $z\max(0,(H_0+XE)/H_0)$ | 同じ「深度」という名前でも固定深度と同一ではない |
| NWSの特例 | 表面（`depth=0`）を0に保ち、それ以外は $z+XE$ | 地域モデル固有の取り扱いを一般化しない |
| `min_water_depth="auto"` | $H_0+XE\le 0$の干出セル・時刻の`diff`を欠測にする | 有効な湿ったセルが一つもない時間スライスは、マスクせずに残す保護処理がある |

この表は実装の説明であり、上記の式を任意のROMSや他モデルにそのまま適用してよいという推奨ではありません。特にσ座標を持つモデルでは、格子、変換式、基準海面、海底深度をモデル仕様に合わせて読みます。

## 5. IBIとGLORYSを使い分ける

IBI再解析`IBI_MULTIYEAR_PHY_005_002`はIberia–Biscay–Irelandを対象とする地域プロダクトで、水平格子は1/36°（約3 km）です。GLORYS12V1の`GLOBAL_MULTIYEAR_PHY_001_030`は全球1/12°（約9 km）の再解析です。製品ID、個別dataset ID、変数、時間平均の種類、取得版は分けて記録します。[IBI公式製品ページ](https://data.marine.copernicus.eu/product/IBI_MULTIYEAR_PHY_005_002/description)／[GLORYS公式製品ページ](https://data.marine.copernicus.eu/product/GLOBAL_MULTIYEAR_PHY_001_030/description)

フランス沿岸のデモで使ったIBIは、日本周辺を含むモデルではありません。日本の事例へ移るときは、GLORYSまたは適切な地域モデルの被覆、沿岸・浅海の再現性、利用可能な変数を確認します。FRA-ROMSは本資料では入力適合性の検討対象であり、実行済みの接続例としては扱いません。

海洋モデルの格子を細かいHEALPixに補間しても、新しい観測情報が増えるわけではありません。温度構造の識別力と誤差の大きさを、格子間隔とは別に評価します。

## 6. 欠測、ゼロ、海陸マスク

値0は有効な温度・海面高度であり得ます。NaNは欠測や除外を表します。候補海域外や陸上、入力の不足、観測と矛盾するセルを、同じゼロとして一括処理しません。

複数の観測重みを掛け合わせる`combine_emission_pdf`は`skipna=False`で積を取るため、ある項が欠測のセルは積も欠測になり、そのセルは消えます（観測重みが一つだけの場合は積を取りません）。また、`optimize_pdf`と、状態確率・経路の計算が読み込む観測重みについては、正の質量が残らない時刻をHMM実行前に検出してエラーにします（`_check_emission_mass`）。`normalize_pdf`自体は警告を出すだけです。潮汐関数の一様重みへのフォールバックは、その関数の定義であり、あらゆる欠測を自動で解決する一般ルールではありません。

新しいデータでは、入力変換後の観測数、各観測重みが定義されるセル数、共通の日時・cell ID、正の重みの総量を図示します。これは地図上の経路を見る前に行う診断になります。
